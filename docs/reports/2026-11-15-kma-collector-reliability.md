# KMA 빈 특보 응답 복구와 수집 진단

## 확인한 원인

운영 `getPwnCd` 읽기에서 공개 SDK는 `totalCount=0`, `items.item=[]`를 반환했고
`pageNo`·`numOfRows`는 없었다. 고정 SDK `b77fc5ad980e5baa0138ec05e7e13af67bd83859`의
`empty_kma_body`는 정상 `03` 응답을 이 형태로 정규화하며 원문에 없는 페이지 필드를
만들지 않는다. 수집기의 완결 검증이 모든 응답에 페이지 필드를 요구해 정상 빈 응답을
`ALERT_PAGE_METADATA`로 거절했다. 제공기관 인증 장애나 실제 특보 누락을 빈 성공으로
바꾼 수정이 아니다. 실제 형상 원장은 Git 밖 `alert-metadata-live.json`에 남긴다.

단기예보의 장기 실행은 완전 정지로 확인되지 않았다. 같은 실행의 DB heartbeat와
356,451개 저장 facts·443개 위치가 관측됐다. HTTP 제한 외 정규화·분배·DB 게시 비용을
구분해야 하므로, 호출 한도 상향만으로 전체 실행 시간을 해결했다고 주장하지 않는다.

## 변경

- 첫 페이지·명시적0개·명시적 빈 item list·두 페이지 필드 생략/NULL의 조합만 완전한 빈
  결과로 받는다. total 누락/잘못된 타입·실제 행 불일치·비어 있지 않은 응답·두 번째 빈
  페이지·잘못된 전체 페이지 metadata는 계속 거부한다. 과거 정상 특보를 해제했다고
  추정하거나 발표·원본을 삭제하지 않는다.
- `WeatherSettings.kma_max_rps` 기본값을20회/초로 바꾼다. 명시적 환경 설정이 우선이므로
  운영의 기존10회/초를20으로 바꾸는 일은 별도 실제 반영 검산 대상이다. SDK의 제한기와
  제한 응답·일시 장애 retry 경계는 그대로 사용한다. 중첩 재시도는 추가하지 않는다.
- `AlertCollectionError.diagnostics`는 고정 stage/metadata 필드·타입과 안전한 페이지/행
  개수/HTTP 상태만 담는다. Dagster op는 이를 `Failure.metadata`로 내보내고 기존 고정
  공개 오류 코드를 설명으로 유지한다. `SyncRun.error`는 기존 코드 그대로여서 공개 특보
  API의 `last_error_code`가 일반 실패로 퇴화하지 않는다. 원문 URL·credential·임의 예외
  문자열은 metadata에 포함하지 않는다.
- KMA의 `fetch_ms`, `normalize_ms`, `publish_ms`, `published_values`, `completed_grids`를
  성공 output과 실패 metadata에 남긴다. 요청/재시도 대기, 정규화·분배, DB 준비·게시를
  구분하며 60초 이상 지나 진행 경계를 만났을 때만 안전한 개수 로그를 남긴다. 행별 로그나
  추가 DB heartbeat 쓰기는 없다. 선행 격자를2→4로 늘려 I/O 대기를 겹치되 응답은 요청
  순서로 소비한다. 각 격자의 기존 행/값/바이트 상한·단일 DB 게시·취소 회수를 보존하며
  대기 자료는 직렬화 raw32MiB/정규화20,000facts 이내다. 이 값은 Python heap/RSS 상한
  측정값이 아니다. 병행 span의 누적 시간이므로 이 수치를 더해
  총 wall time이나 운영 p95로 해석하지 않는다.

합성12개 요청에 각각30ms 비동기 대기를 둔3회 교대 측정에서2개 창은 중앙181.383ms,
4개 창은90.768ms였다. 반환 순서/출력 SHA는 같고 최대 병행2/4·종료 뒤 활성 요청0이었다.
별도 동일 입력6격자/12facts의 전체 게시 DTO도 수집 시각을 고정해 같은 것을 검산했다.
소비자 실패 시 뒤의3개 요청을 취소·회수하고, 창밖의6번째 요청 전에 앞선 DB batch가
실제로 저장되는 조건을 확인했다. 이는 I/O 합성 결과이며 운영 단기예보 전체 개선율은 아니다.

## 검증과 실제 반영 경계

초기2개 창의 WSL PG18 기본 집중94개와 후속 진단2개, Docker PG18 집중96개가 통과했다.
같은 시험의 반복·겹친 수는 합산하지 않는다. 실제 고정 SDK를 `MockTransport`로 실행해
JSON·공식 gateway XML의03 빈 응답을 DB 저장까지 검산했다. 잘못된 빈 페이지8조건,
고정 공개 오류 보존, 안전 metadata, 기존 DB 게시·메모리·취소 계약을 확인했다.
기존 Pydantic 및 Dagster context deprecation 경고는 보존하며 새 경고 억제는 없다.

소유 변경 파일의 Ruff 검사는 통과했다. 초기 시험 실행의 잘못된 import 경로와 공식 형식이
아닌 XML fixture, 테스트의 격자 수 오인은 보조 시험 실패로 보존하고 경로·fixture·oracle만
정정했다.4개 창의 전후 DTO 대조에서는 자동 생성 수집 시각까지 고정하지 않은 초기
oracle 실패를 보존하고, 원천·정규화·수집 시각을 함께 고정한 대조를 통과했다. 운영 장애
성공으로 소급하지 않는다. HTTP 준비와 DB thread 완료 순서 차이로 앞 batch가 정확3개가
아닌6개 저장된 Docker oracle 실패도 보존한다. 전체 요청 전에 최소 한 batch가 저장된다는
계약을 검산하며 이미 더 저장된 정상 동작을 실패로 판정하지 않는다.

최종4개 창의 KMA·중기·특보·overlap 영향 범위157개는 WSL PG18과 Docker PG18에서 각각
통과했다. 같은 런타임4파일 지문이 두 검증 전후 동일했고, 소유 시험 PostgreSQL만 정리했다.
앞선 시험 PG가 fast shutdown 뒤255로 끝난 환경 실패도 보존하며 변화 주체를 추정하지 않는다.
고유 r2 시험 PG에서 같은 소스를 재검산했고 최종 PG·QA 컨테이너 잔여0이다. Git 밖
`weather-qa/final-r3-receipt.json`과 두 로그가 정본이다.

관리자 BFF는 원인 체인과 허용된 단계·필드·숫자를 안전한 진단으로 바꾼 뒤 전달한다.
원문 예외·URL/query·키·SQL·stack·임의 metadata는 브라우저로 보내지 않는다. 기존 인증,
origin·코드 위치·실행 소유 범위·페이지/총시간 상한과 취소·늦은 응답 차단을 유지한다.
목록에는 오류 코드 한 줄, 선택한 실행에는 전체 진단을 표시하며 선행 전체 로그 조회는 없다.

관리자 집중66개와 추가 진단8개는 WSL/Docker에서 각각 통과했다. 겹침은 합산하지 않는다.
최종 타입·변경 lint·공통 정책 가드를 통과했다. 실제 DagsterPage의 목록/선택 상세를
PC1440/mobile375 소스 fixture에서 확인했다. 외부 shell/주소 절은 fixture에서 생략했다.
목록1회와 선택 실행 상세1회만 조회했고 비밀 canary·외부 요청·overflow·pageerror0이다.
소유 브라우저·서버·컨테이너 잔여0이며 운영 배포 UI 수용과 구분한다.

사용자가 정한 테스트·머지 범위로 진행한다. 실제 운영 이미지·명시적 환경 한도·정규 실행
성공은 완료로 주장하지 않는다. 배포 담당은 `KOR_TRAVEL_WEATHER_KMA_MAX_RPS=20`을
반영하고 정기 실행의 fetch/normalize/publish 시간과 실패 상세를 실제 확인해야 한다.
SDK 수정·실제 제공기관 추가 호출·운영 DB 쓰기·수집 취소·배포·원본 삭제는 수행하지 않았다.
