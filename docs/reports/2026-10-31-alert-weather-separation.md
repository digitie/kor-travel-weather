# 2026-10-31 특보의 날씨·지역 오표시 수정

## 재현과 원인

운영 Firefox1440/375에서 대표 지점 10개·9개가 모두 뇌우로 표시됐다.
실제 응답에는 풍랑주의보와 함께 OpenWeatherMap 맑음 코드 800·KMA 강수 없음 코드 0이 있었다.
특보 유무를 날씨 상태보다 우선한 뒤 모든 특보를 storm으로 바꾸는 UI 분기가 원인이었다.
특보가 있는 맑음·흐림·날씨 없음·실제 뇌우를 구분하는 회귀4개가 원 코드에서 실패했다.

적용 지역에도 별개 문제가 있었다. 서울 저장 특보의 원본 필드는 `stnId`, `title`, `tmFc`, `tmSeq`뿐이고
구역 코드는 없었다. 수집 경로는 구역 필드가 없으면 해당 발표 관서의 모든 위치에 복제하고 있었다.
발표 관서 번호·목록 제목·중기예보 코드로 특보 적용 구역을 확정하지 않는다.
기상청은 특보구역의 `REG_ID`와 발표·발효 시각을 별도 자료로 제공한다.
[기상청 공식 특보 자료 설명](https://apihub.kma.go.kr/apiList.do?seqApi=10&seqApiSub=288).

## 수정 계약

- 날씨 아이콘·문구는 실제 SKY/PTY/제공처 날씨 코드로 판단한다. 특보만으로 뇌우를 만들지 않는다.
- 특보 배지는 날씨와 분리하며 API가 해당 위치에 유효하다고 판정한 특보에만 사용한다.
- KMA 위치 특보는 위치 metadata의 `kma_alert_area_codes`와 원문 구조화 구역 코드의 정확한 일치를 요구한다.
  코드 접두사·지역명 부분 일치·발표 관서·중기예보 코드로 대체하지 않는다.
- 구역 정보가 없거나 충돌하면 위치의 활성 특보에서 제외하고 `alert_scope_unverified`로 알린다.
  화면은 적용 지역 미확인 안내를 표시하며 이를 ‘특보 없음’으로 단정하지 않는다.
- `/markers`, 위치 `/latest`, `/nearby`, `/resolve`에 같은 규칙을 적용한다.
  요청 좌표가 관측 지점과 다르면 가장 가까운 지점의 특보구역을 그대로 물려주지 않는다.
- 원문·기존 fact는 삭제하거나 수정하지 않는다. 이번 변경은 API 읽기와 웹 표시다.
  구역이 없는 기존 수집 목록으로 실제 지역 특보를 복원했다고 주장하지 않는다.
  실제 구역 자료 연결이 없으면 미확인으로 남으며 수집기·기존 수집 실행은 유지한다.

## 원 실패와 판정 한계

원 배포 unit `4763de93c5ab4069a94b5f09ccc131e7`은 이미지 build/up 자식0 뒤 웹 포트가 열리기 전

첫 metadata 정산은 API 버전 환경 키를 잘못 제외한 검사에서 adopt 전에 중단했다.

## 후속 요청 — 특보가 없으면 칸 숨김

사용자 요청에 따라 구역 미확인 안내를 지도·상세 화면에서 제거했다.
위치에 유효한 특보가 있을 때만 기존 특보 카드를 렌더링하며, 없으면 문구·자리·여백을 만들지 않는다.
API의 구역 판정과 진단 플래그는 유지하며 미확인 특보를 다시 적용하지 않는다.
WSL 전체287개(QA fixture2개 포함)·타입·lint·Next 빌드와 Docker 정식285개를 통과했다.
첫 WSL 검사 도구의 setter 인자 이동과 Docker의 QA 전용 fixture 경로 실패는 보존하고 보완했다.
이번 변경은 웹만 대상으로 하며 API·수집기·DB를 재배포하지 않는다. 실제 반영 결과는 후속 정산한다.
