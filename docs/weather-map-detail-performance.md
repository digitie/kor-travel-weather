# 날씨 지도 상세 조회 성능 개선

## 원인과 변경

2026-10-21 Odroid 운영 화면에서 가평을 선택한 초기 요청은 관측값 8,670ms, 예보 6,089ms였다. 기존 화면은 두 요청을 `Promise.all`로 기다려 느린 요청 하나가 전체 상세 표시를 지연했고, 위치를 바꾸어도 이전 fetch를 계속 수행했다.

상세용 `_current_value_models_many`는 projection에서 UUID만 고른 후 원본 fact를 다시 조회했다. fact의 실제 키는 `(value_id, known_at)`이며 날짜 파티션도 `known_at`으로 나뉜다. 날짜를 버린 재조회는 여러 날짜의 인덱스를 탐색하고, 같은 UUID의 다른 날짜 revision을 선택할 가능성도 있었다. 추가로 PostgreSQL generic plan에서는 bind된 현재값 우선 정렬식을 기존 expression index와 매칭하지 못했다.

변경은 다음과 같다.

- 후보부터 hydrate 및 특보 유효기간 JOIN까지 정확한 복합 키를 유지한다. 요청 날짜의 최소·최대 범위를 함께 전달해 fact 파티션을 제거한다.
- 위치·복합 키 배열을 bind해 요청 크기와 무관한 SQL 구조를 유지한다. 현재값 우선 정렬의 고정 상수만 literal로 렌더링하고 사용자 입력은 계속 bind한다.
- 관측값과 예보를 독립적으로 표시하고, 각 부분의 실패를 격리한다. 위치 변경·새로고침·unmount 시 이전 두 fetch를 취소하고 늦은 응답을 무시한다.
- 마커 DB 작업은 동시에 최대 2개만 실행하고 인증 조회에 별도 worker 용량 2개를 배정한다. 순수 인증·repository 의존성을 async로 바꾸어 기본 worker가 모두 사용 중이어도 인증 전용 경로에 진입할 수 있게 한다. 대기 중 취소된 마커 요청은 DB 작업 전에 중단하고 500개 초과 입력은 대기 없이 거절한다.
- 조회 한도·정렬·시간 범위·원천 payload와 lineage·공개 DTO를 유지한다. 새 캐시나 인덱스·마이그레이션은 추가하지 않는다.

## 운영 DB 읽기 전용 측정

동일 위치·동일 시각·200행을 대상으로 이전/수정 SQL을 PREPARE하고 custom/generic plan을 각각 강제했다. 두 구현의 전체 model_dump는 동일했다.

| 조회 | 이전 custom / generic | 수정 custom / generic |
| --- | --- | --- |
| 현재값 후보 | 1.633 / 212.831ms | 1.600 / 2.520ms |
| fact 200행 | 63.469 / 106.627ms | 16.686 / 17.771ms |
| fact 실제 탐색 날짜 파티션 | 6 / 6 | 1 / 1 |
| fact shared hit blocks | 4,798 / 4,798 | 1,000 / 1,000 |

수정 후보는 두 모드 모두 `ix_weather_current_values_location_current`를 사용했다. 별도 100행 예보 표본에서는 fact SQL 실행이 약31ms에서 8ms로 감소했다. 이는 대표 위치의 SQL 표본이며, 캐시·수집 부하를 통제한 부하 시험이나 서버 전체 CPU 감소율을 의미하지 않는다.

## 자동 검증

- 최종 제품 커밋: `3aff5ef7501109b2a3863dede062c2323e9f32c0`.
- CI: Python 699개, frontend 218개 테스트 통과. Ruff·ESLint·TypeScript·frontend build·OpenAPI 차이 검사 통과.
- 두 명의 독립 적대적 리뷰: 최종 제품 커밋에 열린 P0/P1/P2 없음. 동기 의존성의 worker 대기를 지적받아 async 진입 경로로 수정했고, 최종 CI에서 회귀를 확인했다.
- 실제 DB 회귀: 단일/다중 위치의 관측·타임라인·예보·특보가 다른 날짜 revision을 읽지 않는지, 만료 특보가 다른 revision의 유효기간을 빌리지 않는지 확인했다.
- UI effect 회귀: 관측/예보 각각의 지연·부분 실패, 연속 선택, 늦은 응답, 빈 검색 결과와 실제 fetch signal 전달을 검증했다.

## 인증 worker 포화 재현과 회귀

SQL·표시 개선만 적용한 첫 검증 배포에서는 연속 선택·확대 시 인증 저장소 503이 약5.3초 후 재현됐다. CPU 제한을 제거해도 재현되어 단순 CPU quota 문제로 판단하지 않았다. 마커 작업이 기본 worker 용량을 소진하면서 동기 인증 의존성이 인증 전용 limiter에 도달하기도 전에 대기하는 경로를 수정했다.

회귀 테스트는 기본 worker 용량을 2로 줄이고 마커 DB 작업 2개를 의도적으로 붙잡는다. 이때 정상 인증이 완료되고 잘못된 token은 401로 거절되는지, 취소된 대기 요청은 499로 DB 작업 없이 끝나는지, 초과 입력은 즉시 422인지, 예외 후 permit이 반환되는지 검증한다. 공유 DB pool 포화나 DB 자체 장애까지 5초 이내 응답을 보장하는 변경은 아니며, 인증 저장소 장애 시 fail-closed 503 정책은 유지한다.

## 실제 UI 검증

운영 DB를 사용하는 검증 API·UI에서 13개 시나리오를 통과했다. 로그인·초기 관측/예보, 감일·강릉·가평 선택, 확대 후 실제 지도 마커(양평 소리산) 클릭, 관측/예보 각각 지연·실패 시 나머지 정보 유지, 빈 검색, 연속 검색의 마지막 선택 유지, 모바일 390px 레이아웃, 로그아웃을 확인했다. JS 오류와 실제 HTTP 오류는 0건이며 실패 격리를 확인하기 위해 주입한 503만 2건 있었다. VWorld 타일은 53건 성공·0건 실패였다.

검증 환경은 공개 Host 및 HTTPS 프록시 헤더를 전달하여 내부 임시 포트로 연결했다. 최종 테스트 커밋 3aff5ef는 이 검증 배포 2f9a0d2와 제품 코드·프론트엔드가 같고 테스트 fixture만 수정했다. 공개 HTTPS 경로는 운영 배포 후 아래와 같이 별도로 검증했다.

### 운영 공개 HTTPS 검증 및 배포

[제품 PR #124](https://github.com/digitie/kor-travel-weather/pull/124)는 2026-10-21 11:26:57 UTC에 머지됐다. NVMe에서 준비한 ARM64 API·UI 이미지 `3aff5ef7`을 두 서비스에만 적용했다. 공유 DB·Dagster daemon/webserver·Weather code-server·Geo·Transport 관련 컨테이너 10개의 ID와 실행 상태가 유지됐다. API health와 공개 API version·UI login은 모두 200이며 version의 git_commit은 최종 제품 커밋과 일치했다. DB 스키마 변경 및 데이터 마이그레이션은 없다.

운영 공개 HTTPS 주소에서 로그인·초기 데이터·감일/강릉/가평 선택·실제 지도 마커 클릭·모바일·로그아웃 등 7개 시나리오가 통과했다. 테스트가 집계한 실제 HTTP 오류 0건, JS 오류 0건, VWorld 타일 57건 성공·0건 실패였다. 지연/실패 주입 검증은 앞의 별도 검증 환경에서 수행했고 운영 테스트에는 주입하지 않았다.

| 운영 선택 | 관측+예보 표시 완료 |
| --- | --- |
| 감일 | 2,098ms |
| 강릉 | 3,672ms |
| 가평 | 3,621ms |
| 실제 지도: 양평 소리산 | 5,239ms |

초기 가평 latest/forecast는 8,670/6,089ms였고, 배포 후 최초 동일 위치 요청은 3,502/3,148ms였다. 다른 시각·부하의 단일 표본이며 모든 위치의 보장 시간은 아니다. 상세가 여전히 수 초 걸리는 경우가 있으므로 이후에는 DB/worker 대기와 payload 직렬화를 분리해 반복 측정할 수 있다.

[운영 UI 결과](reviews/evidence/2026-10-21-weather-map-detail-production.json), [배포 증거](reviews/evidence/2026-10-21-weather-map-detail-deployment.json)에 시나리오·타이밍·이미지 revision·공개 상태를 기록했다. 임시 검증 컨테이너 2개와 임시 인증 환경 파일은 운영 검증 후 제거했고 이전 운영 이미지와 비공개 compose 백업은 롤백용으로 유지한다.

## HTTP 표본과 해석

초기·수정 API를 같은 운영 DB로 비교한 별도 표본은 다음과 같다. 당시 수정 검증 API에는 1 CPU 제한이 있었고 빌드·수집 작업이 함께 실행 중이었다. 전체 내용의 행 수는 같았으며 위치별 결과를 비교했다.

| 위치 | 관측 이전 → 수정 | 예보 이전 → 수정 |
| --- | --- | --- |
| 가평 | 4,048 → 2,174ms | 1,385 → 603ms |
| 감일 | 2,010 → 943ms | 248 → 173ms (0행) |
| 강릉 | 2,079 → 853ms | 1,155 → 358ms |

표본의 부하·캐시 상태가 통제되지 않았으므로 반복 벤치마크의 p95나 전체 CPU 감소율로 해석하지 않는다. 독립 렌더링으로 빠른 정보부터 표시하지만 shared DB 자체의 장시간 대기까지 제거한 것은 아니다.

[검증 UI 결과](reviews/evidence/2026-10-21-weather-map-detail-stage.json), [API 비교 표본](reviews/evidence/2026-10-21-weather-map-detail-api-compare.json)에 시나리오와 측정을 남겼다. 비밀번호·세션·원천 payload·DB 접속 정보는 증거 파일에 포함하지 않았다.
