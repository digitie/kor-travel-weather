# Weather 지도·상세의 공용 구조와 정보 우선순위 개선 설계

작성일 2026-10-25(KST). 상태: **미구현 후속 설계**. 이번 PR은 문서만 변경한다.
[사전 조사](../research/2026-10-25-weather-ux.md),
[Transport 공용 계약·전체 작업 계획](https://github.com/digitie/kor-travel-transport/blob/main/docs/design/2026-10-25-mobility-improvements.md)을 함께 읽는다.

## 1. 설계 범위

기존 admin의 홈·날씨·위치·dataset·수집 이력·Dagster·API-test·설정 메뉴를 유지한다.
소비자처럼 장소·종류·출처로 조회하며 정보를 얻는 경험을 개선하고, 필요한 데이터가 기존 API에 부족하면
해당 API를 보완한다. 화면마다 요청/응답 검사 패널을 추가하거나 새 운영 콘솔을 만들지 않는다.

기존 종류 6종(특보·실황·초단기·단기·중기·관측)·출처 필터와 현재/미래 분리·특보 효력 판정은 보존한다.
사용자 보고는 실제 운영 수용 문제다. 소스에 overlay가 이미 있다는 이유로 문제를 해소했다고 하지 않는다.
운영 릴리스 차이와 부모 shell·높이·스타일 문제를 먼저 대조한다.

## 2. 공용 지도 작업면과 프로젝트 톤

공유 작업 **C-MAP-01**의 소유자는 Common이다. Map `origin/main@c06345841`의 Feature 지도 외곽·compact shell,
기존 공용 필터/탭/읽기값/상세를 정본으로 묶는 작업이다. Weather는 별도 지도 프레임을 새로 만들지 않는다.
도메인 데이터 조회·선택 상태·기상요소 해석은 Weather 소유로 남긴다.

```text
기존 shell의 간결한 제목 + i + 필요한 행동
종류 · 장소 검색 · 데이터 출처 (+펼쳐 쓰는 시간/요소 조건)
지도/목록 전환                         n건 · center 경도, 위도 · z 줌
단일 stage: 지도/목록 · 선택 상세 overlay · 범례 · 지도 제어/attribution
```

현재 `MapFilterBar/Field/KindFilter`, `MapTabs/TabPanel/ViewTabs`, `MapDetailOverlay`를 재사용한다.
34rem·70dvh 고정/덮어쓰기와 legacy layout의 중복을 제거해 실제 가용 높이를 stage로 전달한다.
조상 flex/grid `min-height:0`, 단일 스크롤, 지도 resize·가림·safe area까지 같은 계약으로 확인한다.
공용 구조 변경은 Common과 Map 소비자 회귀를 거친 후 Weather/Transport에 같은 버전으로 인계한다.

다음은 새 수용 목표이며 현재 운영 실측값이 아니다. Transport 계약과 동일하다.

| 환경 | 수용 기준 |
|---|---|
| PC 1440×900 | 종류·검색·출처 기본 한 줄, 컨트롤 높이 30px/검색·출처 폭 176px. stage 하단은 가용 화면 하단과 24px 이내. 중첩 카드 여백 없음 |
| 모바일 375×812·390×844 | 키보드 닫힌 지도 모드에서 stage 시작 상단 240px 이내·남은 높이 활용. 긴 조건/검색 후보가 지도를 아래로 밀지 않음 |
| 320×568·가로·글자 200% | 지도 바로 이동/확장 제공, 조건 접기·해제 가능. 한 줄 강제/작은 글씨 압축 없이 지도 조작부 접근 |
| 상세/목록 | 상세는 같은 stage 내부. 모바일 기본은 핵심 정보만. 닫기/접기·Escape·초점 반환·목록 대안, 지도 제어/attribution 가림 방지 |
| 브라우저 | iOS Safari/Android Chrome 주소창·키보드·회전·복귀, PC Firefox/Chromium의 타일·드래그·선택·뷰 전환 |

모바일 상세의 배치 보강도 공용 계약에서 정의한다. Weather만 다른 drawer를 새로 디자인하지 않는다.
유가·철도·도로와 같은 외곽을 쓰되 Weather의 기상 내용은 별도 슬롯으로 유지한다.

현재 `app/tokens.css`와 `design.md`의 Weather navy를 정본으로 `--kt-*`에 의미별 연결한다.
brand/hover/tint·surface·text·border/control-line·focus·상태·그림자·popover·차트까지 확인한다.
Common 기본 녹색이 일부 버튼에 남거나 Map의 색을 그대로 덮어쓰지 않게 한다. light/dark도 함께 확인한다.
특보·강수·온도 범례의 의미색은 브랜드색과 분리하고 색만으로 구분하지 않는다.

## 3. 상세 정보의 우선순위와 취향

선택 상세의 순서는 **위치·닫기 → 해당 위치의 유효 특보 → 선택 시각의 현재/예보 핵심값 → 이후 시간별 흐름 →
일별/중기 참고 → 필요한 출처 설명**이다. 모든 metric·원본 행을 처음부터 크게 나열하지 않는다.

- 위치·시각이 고정된 한 맥락에서 기온·강수확률/양·바람을 먼저 읽게 한다. 단위와 관측/예보 표기를 값 옆에 둔다.
  원천 미제공은 ‘없음/맑음/0’으로 바꾸지 않는다. 같은 시간 열의 값이어야 한다.
- 관심 요소 순서·관심 장소·표/그래프 선호는 가벼운 사용자 선택으로 검토한다. 기본 목록의 유용성을 먼저 확인하고
  목적별 새 페이지나 설정 마법사를 만들지 않는다. 등록하지 않은 장소도 검색할 수 있어야 한다.
- 현재·이후 몇 시간·방문일 시간대를 기존 작업면에서 선택한다. 단기 시간별, 중기 오전/오후·일별 해상도를 보존하고
  해당 시각 자료가 없으면 지원 범위를 명시한다. 현재 날씨 위에 미래 예보를 섞지 않는다.
- 지도는 선택 요소·유효 시각을 범례와 함께 표시한다. 상세와 마커가 다른 시간/제공처 값을 보여주는 상태를 막는다.
  먼저 기존 marker/forecast API 범위를 확인하고 필요한 선택 조건만 보완한다.
- 발표 시각·유효 시각·관측 시각·수집 시각은 서로 다르다. 긴 제공처/dataset/원본 ID·정의는 제목 옆 `i`로 옮기되
  실제 갱신 지연·특보·선택 시각을 해석하는 데 필요한 상태는 해당 값 가까이에 남긴다.
- 측정소의 값이면 측정소·거리·시각을 확인할 수 있어야 한다. 근처 측정소를 선택 장소의 실측이라고 이름 붙이지 않는다.
  기존 산악·해양·휴게소·AirKorea 자료는 제공 위치·해상도에 맞게 표시한다.
- 시간축의 가로 스크롤을 페이지 탭 전환으로 사용하지 않는다. 지도 드래그와 상세 스크롤도 구별하고 키보드 대안을 제공한다.
  접힌 안내는 반복하지 않으며 빈 데이터·갱신 실패는 정상 0과 구분한다.

출발지/목적지·방문 시각을 알고 들어오면 입력을 보존하는 연결을 검토한다. 자체 여정 플래너·새 알림 시스템이나
근거 없는 활동 안전/개인 건강 판정을 만드는 범위는 아니다.

여기서 ‘등록 없이 검색’은 우선 **계정/즐겨찾기 등록 없이 저장된 enabled 위치를 검색**한다는 뜻이다.
Weather DB에 없는 여행 목적지는 이름 검색만 추가해서 날씨가 제공된다고 표시하지 않는다.
목적지 이름→좌표 변환은 Geo 등 기존 정방향 장소 검색 계약의 제공 범위·인증·한도를 먼저 확인해 재사용한다.
현재 Weather의 역지오코딩 주소 갱신은 이름→좌표 검색 기능이 아니다. 정방향 검색을 쓸 수 없거나 이름이 모호하면
지도에서 지점을 선택하거나 전달받은 좌표를 쓰도록 안내한다. 후보 이름·좌표를 사용자가 확정한 뒤 기존 resolve/nearby의
**저장된 anchor**를 재사용하고, 목적지와 대표 관측/예보 지점의 차이·거리를 표시한다.
선택 provider/kind에 적합한 anchor·값을 거리 정렬/LIMIT 전에 고르는 보강이 필요하다. 현재 두 API에는 그 필터가 없다.
반경 안에 적합한 저장 자료가 없으면 미제공으로 끝내고 임의 location 자동등록·collector 활성화·원천 추가 조회로 이어지지 않는다.

## 4. 기존 API를 활용하는 변경

기존 경로는 `packages/kor-travel-weather-api/src/kortravelweather_api/routers/weather.py`와 OpenAPI가 정본이다.
다음은 후보 변경이며 새 계약을 이미 제공한다는 뜻은 아니다.

| 필요한 경험 | 재사용 대상 | 보강이 필요한 경우 |
|---|---|---|
| 장소·근처·범위 검색 | locations의 이름/provider/kind 검색, 좌표를 받는 nearby·resolve | 계정/즐겨찾기 등록·위치 권한 없이 catalog 검색. DB 밖 목적지는 검증한 기존 이름→좌표 검색 또는 지도 지점 선택→저장 anchor 조회. nearby/resolve에 필요한 provider/kind를 선택적으로 보강해 거리 정렬/LIMIT 전 적용. 적합 anchor 부재는 미제공이며 자동등록/원천 호출 없음 |
| 특정 시각의 시간별/중기 비교 | `/locations/{location_id}/forecast`의 from/to·metric_key·dataset·history·provider/kind | UI가 임의로 전체 값 중 일부를 잘라 시간 창을 왜곡하면 범위/완결 표시를 보완. target/issued 시간 의미 유지 |
| 지도 마커와 상세의 시간·요소 일치 | 기존 marker 묶음 읽기·latest/forecast 분리 | 기존 한도/선택을 검토해 필요한 시간·요소 조건을 선택적으로 추가. 다른 발표본/제공처의 값 혼합 방지 |
| 특보 우선 표시 | 기존 활성 특보·효력 판정 | 지역 범위·발효/해제·출처 필드가 부족한 부분만 보강. 조회 실패를 특보 없음으로 변환하지 않음 |
| 주소/위치·실행 연결 | 기존 location ID/좌표와 sync-runs·Dagster | 주소 클릭→같은 지도 선택, 기존 run의 확인된 ID→Dagster 원본. 내부 URL·키 노출 금지 |

같은 조건의 외부 API 소비자도 UI와 같은 데이터 의미·기간·오류 상태를 얻어야 한다. 화면 전용 가짜 파생값이나
전체 응답에 새 진단 envelope를 추가하지 않는다. DTO/OpenAPI/TypeScript와 계약·통합 테스트는 해당 변경에 맞춰 갱신한다.
원천 필드 의미·파싱 문제는 KMA 등 기존 SDK에서 개선하며 backend provider 우회 wrapper를 만들지 않는다.
이미 구현된 서비스 export W1~W5와 승인 head·쿼터·읽기 한도·운영 활성화는 별도 계약으로 보존한다.
이 설계만으로 collector/publisher를 켜거나 추가 원천 호출을 시작하지 않는다.

## 5. 작업과 수용 기준

모든 항목은 후속 미구현 작업이다. [tasks.md](../tasks.md)에서 추적한다.
P0는 사용자가 필요한 지도 접근/기본 기능, P1은 정보 우선순위·선택과 계약 개선이다.

| ID | 소유·선행 | 완료 조건 |
|---|---|---|
| C-MAP-01 / P0 | Common 담당, Transport와 공유 | Map 기준 공용 외곽·가용 높이·상세 슬롯/테마 계약. Map 회귀·패키지/버전 인계. Weather에서 중복 구현하지 않음 |
| W-UX-01 / P0 | Weather shell/map/CSS/tokens. C-MAP-01 뒤 | 실제 배포 버전/치수 대조, §2 전 크기·브라우저·토큰/초점·타일 수용. Transport T-MAP-01과 동일 외곽 |
| W-UX-02 / P1 | Weather 상세/시간축·기존 읽기 API | §3 정보 순서·선택 시각·관심 요소·출처 i, 정상 0/오류/지연·관측/미래 분리. 긴 메타데이터가 먼저 보이지 않음 |
| W-UX-03 / P1 | Weather core/API/DTO/OpenAPI/TS·연결. W-UX-02 및 기존 Geo 이름 검색 계약 대조 뒤 | catalog/즐겨찾기 등록의 의미 구분, DB 밖 목적지 좌표→적합 저장 anchor와 대표성/부재 수용. 기존 forecast/marker 재사용·필요 조건만 보강, LIMIT/완결·효력/단위/제공처 일관성, 주소/run/교통 복귀 링크 |

구현 시나리오:

1. 위치 허용/거부 모두 장소 검색, 종류/출처 변경→같은 조건의 지도/목록/상세. 이전 요청 지연 응답의 덮어쓰기 방지.
2. 현재·미래·단기·중기·특보 각 선택 시 target 시각·발표본·단위 일치. 현재 맑음과 미래 비/다른 기온을 섞지 않음.
3. 이후 몇 시간/방문일에 자료 없음·일부 잘림·다른 제공처·측정소 거리·stale/실패를 구분. 정상 empty와 서버 오류 분리.
4. 375/390px 첫 화면 지도 접근·최대 활용, 320px/가로/글자 200%와 PC Firefox/Chromium. iOS Safari/Android Chrome에서
   주소창·키보드·회전·외부 복귀·가로 시간축·지도 드래그·닫기/Escape·초점 반환 확인.
5. 날씨 주소/좌표→해당 위치 지도, 교통 화면에서 방문 장소/시각 연결 시 입력 보존. sync-run→확인된 Dagster run 연결.
6. 위 데이터 시나리오를 직접 API에서도 검증. 합성 fixture 통과와 실제 운영 자료/릴리스 수용을 분리 기록.
7. 즐겨찾기 없는 catalog 위치, DB 밖 목적지의 이름/동명이름·Geo 미지원·지도 지점 선택, 반경 내 적합 anchor 없음,
   provider/kind에 맞지 않는 가까운 anchor를 각각 시험한다. 목적지·대표 지점의 거리/종류를 확인하고 자동등록·추가 수집이 없어야 한다.

구현 PR의 테스트·CI·독립 리뷰·운영 활성화 게이트는 평소 규칙을 따른다.
이번 **문서 PR만** 사용자 지시에 따라 두 차례 문서 정합 점검 후 독립 적대적 리뷰어 1명에게 양쪽 저장소를 검토받고
CI 결과를 기다리지 않고 머지한다. 실제 결과는 [검토 기록](../reports/2026-10-25-weather-design-review.md)에 남긴다.
