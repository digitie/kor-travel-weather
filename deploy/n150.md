## 배포

원격 `~/kor-travel-weather/.env`는 모드 `600`으로 유지하고 Git에 추가하지 않는다.
비밀값은 password manager/secret manager에서 일회성으로 주입하고, 저장소 작업
복사본에는 평문 secret 파일을 남기지 않는다. `KOR_TRAVEL_WEATHER_CREDENTIAL_ENCRYPTION_KEY`와
`KOR_TRAVEL_WEATHER_METRICS_TOKEN`도 API와 관련 서비스에 동일하게 주입해야
`/settings/providers`에서 암호화된 DB override를
저장할 수 있다. KMA service key와 수집 target은
운영자가 발급·검토한 뒤에만 원격 secret store에서 주입한다.

```bash
# 예: 보호된 로컬 secret 파일을 사용한다(저장소 안에 만들지 않는다).
scp /secure/path/kor-travel-weather-n150.env digitie@192.168.1.14:~/kor-travel-weather/.env
ssh digitie@192.168.1.14 \
  'chmod 600 ~/kor-travel-weather/.env && cd ~/kor-travel-weather && \
   git fetch origin && git checkout main && git pull --ff-only && \
   GIT_COMMIT=$(git describe --always --dirty --abbrev=7) docker compose --env-file .env \
     -f compose.yaml -f deploy/compose.n150.yaml up -d --build'
```

### 0015 이후: `weather_values` 인덱스는 사전 생성해도 소용없다

`0015`가 파티셔닝을 위해 `weather_values`를 **재작성**하므로, 그 테이블의 인덱스는
어차피 전부 다시 만들어진다. 미리 만들어 둔 것은 재작성과 함께 사라진다.
사전 생성이 여전히 의미 있는 것은 **프로젝션 인덱스**
(`ix_weather_current_values_*`)뿐이다. `test_migration_leaves_a_pre_built_index_alone`이
이 구분을 강제한다 — fact 인덱스가 다시 만들어지지 않게 되면 그 테스트가 실패하고,
그때 이 문단을 되돌리면 된다.

아래 사전 생성 절차는 `0015` **이전** 스키마에서 올라오는 경우의 기록이다.

### 인덱스 마이그레이션은 배포 창 밖에서 먼저 만든다

`0009`~`0011`과 `0013`은 `CREATE INDEX CONCURRENTLY`를 쓴다. CONCURRENTLY는 병렬 워커를
쓰지 않고 테이블을 두 번 훑으며, `weather_values`는 2천만 행/28GB 규모다.
API와 Dagster는 `migrate: service_completed_successfully`에 묶여 있으므로 그
빌드가 끝날 때까지 **공개 API가 내려가 있다**. 인덱스 4개를 배포 중에 만들면
그 창이 수십 분에 이를 수 있다.

배포 전에 psql로 먼저 만들어 두면 마이그레이션의 `IF NOT EXISTS`가 그대로
통과한다. 이름만 같으면 넘어가므로 **아래 문장을 그대로** 써야 한다 — 정의가
다르면 마이그레이션은 손대지 않고, 잘못된 인덱스가 그대로 남는다.

```bash
ssh digitie@192.168.1.14 'docker exec -i kor-travel-weather-db-1 \
  psql -v ON_ERROR_STOP=1 -U weather -d weather' <<'SQL'
CREATE INDEX CONCURRENTLY IF NOT EXISTS ix_weather_values_marker_observed
  ON weather_values (location_id, metric_key, known_at DESC NULLS LAST,
                     source_record_key DESC NULLS LAST, value_id DESC)
  WHERE metric_key IN ('TEMP', 'T1H', 'TMP', 'WEATHER_CODE', 'SKY', 'PTY')
    AND forecast_style IN ('observed', 'nowcast');
CREATE INDEX CONCURRENTLY IF NOT EXISTS ix_weather_values_alert_lookup
  ON weather_values (location_id, target_at DESC)
  WHERE weather_domain = 'weather_alert' OR metric_key = 'ALERT';
CREATE INDEX CONCURRENTLY IF NOT EXISTS ix_weather_current_values_alert_lookup
  ON weather_current_values (location_id, target_at DESC)
  WHERE metric_key = 'ALERT' OR weather_domain ILIKE '%alert%'
     OR weather_domain ILIKE '%warning%' OR dataset_key ILIKE '%alert%'
     OR dataset_key ILIKE '%warning%';
SQL
```

`0013`의 인덱스는 `0012`가 추가하는 컬럼 위에 만들어지므로 같은 블록에 넣을 수
없다. 위 블록에 섞어 두면 스키마가 아직 `0011`이라 `column "known_at" does not
exist`로 실패하는데, **psql은 그래도 exit 0을 반환**해 운영자는 네 개가 다
준비됐다고 믿게 된다. 그래서 `-v ON_ERROR_STOP=1`을 쓰고, 0012만 먼저 적용한 뒤
별도 블록으로 만든다. 0012는 아래 설명대로 API를 막지 않는다.

0012를 적용하기 전에 **수집을 멈춘다.** 백필은 한 문장이라 도는 동안 포인터 행
락을 전부 쥐고, publish 중인 이전 릴리스가 그 뒤에서 멈춘다. 더 중요한 건 반대
방향이다 — 장기 publish 트랜잭션이 하나라도 열려 있으면 `ADD COLUMN`이
`ACCESS EXCLUSIVE`를 영영 못 잡아 30회 재시도 끝에 실패한다. 실제로 겪었다:
1시간 49분 열린 채 advisory lock을 쥔 publish 하나 뒤로 4개가 직렬로 밀려 있었다.

```bash
ssh digitie@192.168.1.14 'cd ~/kor-travel-weather && \
  docker compose --env-file .env -f compose.yaml -f deploy/compose.n150.yaml \
    stop dagster-webserver dagster-daemon dagster-code-server dagster-gateway'

# 남은 장기 트랜잭션이 없는지(0인지) 확인한 뒤에 진행한다.
ssh digitie@192.168.1.14 "docker exec kor-travel-weather-db-1 \
  psql -U weather -d weather -Atc \"SELECT count(*) FROM pg_stat_activity \
  WHERE datname='weather' AND xact_start < now() - interval '30 seconds'\""

ssh digitie@192.168.1.14 'cd ~/kor-travel-weather && \
  docker compose --env-file .env \
    -f compose.yaml -f deploy/compose.n150.yaml \
    run --rm migrate alembic upgrade 0012_current_value_sort_keys'

ssh digitie@192.168.1.14 'docker exec -i kor-travel-weather-db-1 \
  psql -v ON_ERROR_STOP=1 -U weather -d weather' <<'SQL'
CREATE INDEX CONCURRENTLY IF NOT EXISTS ix_weather_current_values_location_current
  ON weather_current_values
  (location_id,
   (CASE WHEN forecast_style IN ('observed', 'nowcast') THEN 0 ELSE 1 END),
   target_at DESC, known_at DESC NULLS LAST,
   source_record_key DESC NULLS LAST, value_id DESC);
SQL
```

Dagster 수집이 도는 시각(매시 정각·10분)은 피한다. CONCURRENTLY는 동시
트랜잭션이 끝나기를 기다리므로, 대량 publish 트랜잭션 뒤에서 그만큼 지연된다.
인덱스 빌드가 실패해 INVALID 인덱스가 남아도 해당 마이그레이션이 회수하고 다시
만든다(`indisvalid`만 확인한다). 이는 인덱스 리비전(0009~0011, 0013)에 대한
이야기다 — 0012는 인덱스를 만들지 않고, 대신 위 설명대로 재실행 안전하다.
**migrate 컨테이너를 중간에 죽이지 말 것** — 다음 시도가 처음부터 다시 돈다.

### 0012는 사전 생성 대상이 아니다 (그럴 필요도 없다)

`0012`는 인덱스가 아니라 `weather_current_values`에 컬럼 두 개를 더하고 채운다.
nullable 컬럼 추가는 카탈로그만 바꾸므로 `ACCESS EXCLUSIVE`를 밀리초 단위로만
잡고 테이블 재작성이 없다. 이어지는 백필은 평범한 `UPDATE`를 배치로 돌아 행
잠금만 쓰므로 **읽기를 막지 않는다**. 둘을 한 문장으로 합치면 28GB 팩트 테이블
순차 스캔 내내 배타 잠금을 쥐게 되어 API 전체가 멈추는데, 그래서 나눠 놓았다.

백필은 이어서 돌릴 수 있다. 고치는 대상은 "키가 비어 있는 행"이 아니라 **"키가
가리키는 팩트와 어긋난 행"**이다. 이전 릴리스는 포인터를 옮길 때 `value_id`만
쓰므로(새 컬럼이 모델에 없다) 그 행은 새 팩트를 가리키면서 이전 팩트의 키를
그대로 들고 있게 된다 — 비어 있지 않고 틀린 상태다.

백필은 **한 문장으로** 돈다. 배치로 쪼개면 팩트 조회가 랜덤 IO가 되는데, 이 DB는
초당 약 160 랜덤 읽기밖에 못 낸다 — 프로덕션(3.75M 포인터 / 33GB 팩트)에서 실측
160행/s, 완료까지 6시간이었다. 한 문장이면 플래너가 포인터 쪽을 해시로 잡고 팩트
테이블을 **순차로 한 번** 훑으므로 랜덤 읽기가 아예 사라진다.

**아무것도 고치지 않은 pass는 그 자체로 완료 증명**이므로 별도 검증 질의가 없다.
두 번째 pass는 확인용이고, 이전 릴리스가 아직 포인터를 옮기고 있으면 그 행들을
여기서 잡는다.

이 문장은 테이블 락이 아니라 행 락을 잡으므로 **읽기는 막지 않는다**. 다만 pass가
도는 동안 모든 포인터 행에 행 락을 쥐므로, 이전 릴리스가 동시에 publish 중이면
그쪽이 멈춘다 — 그래서 위에서 수집을 먼저 멈춘다. 컬럼 추가도 `IF NOT EXISTS`다. alembic은 `upgrade()`가 끝난 뒤에야 버전을 기록하므로, 그
전에 커밋되는 것은 전부 다시 실행해도 안전해야 한다.

컬럼은 nullable로 둔다. compose는 이전 릴리스가 아직 수집·서빙하는 동안
migrate를 돌리고, 그 릴리스는 새 컬럼 없이 포인터 행을 쓴다. 여기서 `NOT NULL`을
걸면 배포 도중 수집이 깨진다. 그 창에서 쓰인 행은 정렬에서 뒤로 밀리고
(`nullslast`) 해당 논리 지점의 다음 리비전에서 키를 얻는다.

### 0015: 팩트 테이블 파티셔닝

`0015`는 `weather_values`를 `known_at` 기준 **일별 파티션 테이블로 재작성**한다.
기존 테이블을 그대로 `ATTACH` 할 수는 없다 — 옛 기본키에 파티션 키가 없어서
부모의 제약을 만족하지 못한다. 그래서 행을 옮긴다: 순차 읽기 한 번, 순차 쓰기
한 번으로, 이 디스크가 잘하는 작업이다.

**수집을 먼저 멈추고, 공개 API 다운타임을 예고하라.** 재작성은 `weather_values`에
`ACCESS EXCLUSIVE`를 잡는다. `/nearby`는 알림 조회 때문에 그 테이블을 읽으므로
재작성이 끝날 때까지 **504로 응답한다**. `/health`와 `/markers`는 영향이 없다.

실측: 3.8M행 / 5.4GB 재작성에 **약 43분**(09:37→10:20). 커밋 직후 몇 분은 통계가
없어 더 느리다 — 마이그레이션이 `ANALYZE weather_values`로 마무리하지만
autovacuum과 겹치면 그 시간이 늘어난다. 여유를 두고 창을 잡아라.

바뀌는 것:

- 기본키가 `(value_id, known_at)`, 식별 제약에 `known_at`이 추가된다.
- 프로젝션 FK가 복합키 `(value_id, known_at)`가 되고 `known_at`이 NOT NULL이 된다.
  `0012`가 채워 둔 값이라 승격은 검증만 하고 지나간다.
- 이후 정리는 배치 DELETE가 아니라 **파티션 DETACH + DROP**이다.

```bash
ssh digitie@192.168.1.14 'cd ~/kor-travel-weather &&   docker compose --env-file .env -f compose.yaml -f deploy/compose.n150.yaml     stop dagster-webserver dagster-daemon dagster-code-server dagster-gateway'

ssh digitie@192.168.1.14 'cd ~/kor-travel-weather &&   GIT_COMMIT=$(git describe --always --dirty --abbrev=7)   docker compose --env-file .env -f compose.yaml -f deploy/compose.n150.yaml     run --rm migrate alembic upgrade head'
```

적용 후 확인한다. `relkind='p'`가 파티션 부모이고, DEFAULT에 행이 있으면
그 행들은 **다시는 정리되지 않는다**.

```sql
SELECT relkind FROM pg_class WHERE relname = 'weather_values';
SELECT count(*) FROM pg_inherits i JOIN pg_class p ON p.oid = i.inhparent
  WHERE p.relname = 'weather_values';
SELECT count(*) FROM ONLY weather_values_default;
```

### 0017: 앞쪽 파티션과 DEFAULT 바닥(floor)

`0015`는 이미 행이 있는 날짜에만 파티션을 만들었다. 2026-09-20의 새 DB는 비어
있었으므로 날짜 파티션이 하나도 생기지 않았고, 야간 정리 job은 DEFAULT에 행이 생긴
뒤로는 파티션을 만들 수 없었다(만들려면 DEFAULT 전체를 `ACCESS EXCLUSIVE` 아래서
훑어야 하고, 2026-09-30에는 수집과 교착했다). 모든 fact가 DEFAULT로 들어가 36GB가
됐고 insert마다 메모리보다 큰 인덱스를 무작위로 읽었다.

`0017`은 DEFAULT가 **비어 있을 때만** 바닥 제약 `CHECK (known_at < 어제)`를 걸고
어제~+7일 파티션을 만든다(빈 테이블이라 즉시). 그 뒤 야간 job은 바닥 이후 날짜만
만들므로 DEFAULT를 읽지 않는다. 바닥 이후로 앞쪽 창(`RETENTION_AHEAD_DAYS`)을 넘는
날짜의 fact는 DEFAULT로 새지 않고 거부된다 — 의도한 교환이다.

DEFAULT에 행이 있으면 `0017`은 아무것도 하지 않는다. 배포 **뒤에** 운영자가 돌린다:

```bash
# 비파괴. 한산한 시간(KST 새벽)에, 바닥(다음 KST 자정)보다 3시간 이상 앞서 돌린다.
# 1) 바닥 NOT VALID 추가(ms) 2) 한 transaction 안에서 VALIDATE(SHARE UPDATE EXCLUSIVE,
#    수집 계속, 21GB 순차 읽기 수십 분) + 내일~+N일 파티션(각 ms).
# lock 대기는 deadlock_timeout×3 — autovacuum이 막고 있으면 취소된다. 실패하면 바닥을 지운다.
docker exec -i kor-travel-weather-dagster-code-server-latest   python - --dry-run < scripts/weather_values_forward_partitions.py
docker exec -i kor-travel-weather-dagster-code-server-latest   python - < scripts/weather_values_forward_partitions.py
```

**스크립트가 도는 동안 weather code-server를 재시작·재배포하지 말 것.** 스크립트는
SIGTERM을 받으면 바닥을 지우고 끝나지만(검증 전이면), SIGKILL이나 grace 초과로 죽으면
검증 안 된 바닥이 남는다. 그때는 스크립트를 다시 돌리면(또는 야간 job이) 먼저 그것을 지운다.

옛 DEFAULT 행 정리(소유자 승인 2026-10-01)는 `scripts/weather_values_purge_default.py`다.
기본은 dry-run(크기, `RETENTION_DAYS` 기준 cutoff, cutoff 이전 행 추정, 프로젝션 FK 영향)이다.
`--execute`는 바닥으로 전략을 고른다:

- DEFAULT 전체가 보존 기간을 지났으면(바닥 ≤ cutoff): 프로젝션 포인터를 먼저 지우고,
  짧은 DDL transaction 둘로 나눈다(nightly의 detach/drop과 같다). 첫째는 프로젝션 FK를 내리고
  DEFAULT를 detach해 `weather_values_default_detached`로 이름을 바꾸고, 같은 바닥의 빈 DEFAULT를
  만들고 FK를 NOT VALID로 다시 건다. 둘째는 떼어낸 옛 DEFAULT를 drop한다. 둘 다 필요한 lock을
  수집 순서(참조 테이블 → fact → 프로젝션)로 처음에 모두 잡고 중간에 승격하지 않으며, 지면
  `pg_locks`가 조용해질 때까지(최대 30초) 기다렸다 다시 시도한다(최대 20번). 카탈로그 변경뿐이라
  writer 대기는 ms다. 그 뒤 FK를 SHARE UPDATE EXCLUSIVE로 검증한다(writer 계속). 공간은 drop이
  commit될 때 돌아온다. 둘 사이에서 멈췄으면 다시 `--execute`하면 옛 DEFAULT만 drop하고 끝난다
  (그동안 nightly는 그것이 인용하는 source record를 지우지 않는다).
- 아직 보존 기간 안의 행이 있으면: 만료 행만 2,048페이지(16MB)씩 짧은 transaction으로
  지우고(ROW EXCLUSIVE, writer 계속) 끝나면 throttle한 VACUUM을 돈다. 만료 행이 없으면 거부한다.

운영 `RETENTION_DAYS`는 2026-10-13부터 **7**이다(소유자 결정, 이전 16; 코드 기본값은 2 그대로,
n150 Manager `.env`의 `KOR_TRAVEL_WEATHER_RETENTION_DAYS=7`). PinVi의 최소 요구 보존 기간도 같은
날 7일로 내려갔으므로 운영 값을 7 미만으로 내리면 PinVi를 깬다. 운영 DEFAULT의 바닥은
2026-10-03 00:00 KST(그 이전 `known_at` 행만 있음)이므로, 7일 보존에서는 cutoff가 바닥을 지나는
**2026-10-10 00:00 KST 이후** DEFAULT 전체가 만료이고 `--execute`는 swap(전체 detach+drop)을 고른다.
dry-run도 `--retention-days`를 받는다(기본은 code-server의 `RETENTION_DAYS`).

앞쪽 파티션이 3일 이하로 남으면 `KorTravelWeatherForwardPartitionsLow`가 울린다
(`ktw_forward_partition_days`, API `/metrics` scrape 때 카탈로그에서 읽는다. API만 내보내며
규칙도 `job="kor-travel-weather-api"`만 본다 — 이 값을 계산하지 않는 Dagster code-server가
0을 내보내 오경보가 날 뻔했다).

**야간 정리(`weather_retention_job`)는 lock 경합에 지면 그날 하루치를 미룬다.**
2026-10-02·03·05에 run 전체가 `LockNotAvailable`(`LOCK TABLE weather_values IN ACCESS
EXCLUSIVE MODE`, 앞쪽 파티션 생성 단계)로 실패했다. 수집은 쉬지 않는데 2분 안에 20번
무작정 시도했기 때문이다. 이제는 날짜 하나를 만들거나 떼거나 지우는 일을 각각 짧은
transaction으로 하고, 몇 번 시도하며 그 사이에는 fact 테이블을 아무도 잡지 않은 순간을
기다린다. 그래도 지면 그 날짜는 run metadata(`partitions_deferred`·`partitions_not_created`)에
남기고 다음 run이 다시 한다(run은 초록). 이틀 연속 놓친 날짜(`partitions_overdue`)가 있거나
앞쪽 창이 3일까지 줄었으면 `partial`, 거기에 이번 run이 아무것도 진척하지 못했으면 실패다.
"놓쳤다"는 해야 했는데 못 한 날짜다(시도했다 졌거나 차단기가 건너뛴 날짜). 그런 날짜에는 테이블
COMMENT로 표시를 남기고, 앞선 run이 남긴 표시가 있을 때만 overdue다(job이 돌지 않은 밤은 놓친 것이
아니다). COMMENT는 짧은 lock timeout으로 세 번 시도하고, 그래도 지면 `partitions_unmarked`에 남겨
asset observation(테이블 잠금·마이그레이션 없음, run이 실패해도 기록)으로 다음 run에 넘기며 다음
run은 그것을 표시로 친다. detach와 drop은 따로
commit하므로 drop만 밀린 날짜(떼어낸 테이블)가 남을 수 있다. 그동안은 다음 날짜를 떼지 않아
남는 것은 많아야 하나이고(이렇게 보류된 날짜는 표시하지 않는다 — 놓친 것은 앞의 drop이다),
`ktw_oldest_partition_age_days`도 그것을 센다. source purge는 그
테이블이 가리키는 source만 남기고 진행한다. 같은 종류(앞쪽 생성, 또는 detach/drop — 차단기가
따로라서 앞쪽 생성이 막혀도 보존 정리는 굶지 않는다)의 미룸이 세 번 연속이면 run은 그 종류의
나머지를 미루고 멈춘다(`partition_ddl_stopped`, 2시간 상한 보호). 마지막 FK VALIDATE는 10분 statement_timeout을
넘으면 NOT VALID로 두고 다음 run이 검증한다.

받아들인 한계(2026-10-07 리뷰, LOW): DEFAULT 때문에 `DETACH CONCURRENTLY`를 못 쓰므로 detach마다
fact 테이블 ACCESS EXCLUSIVE가 잠깐 필요하다(대기는 lock timeout 하나로 묶임). API의 현재값 조회가
드물게 교착 희생자가 될 수 있다(`ddl_lock_timeout_ms` 참고, 재시도 가능). 운영 스크립트의 DEFAULT
swap(`weather_values_purge_default.py --execute`)은 원래 같은 transaction에서 DEFAULT를 drop해서 참조
테이블 ACCESS EXCLUSIVE를 문장 중간에 잡았다(2026-10-13 검토: DROP이 참조 테이블 lock을
SHARE ROW EXCLUSIVE에서 ACCESS EXCLUSIVE로 승격해, 그것을 읽고 fact를 기다리던 수집·API 세션과
교착할 수 있었다). 같은 날 nightly처럼 두 transaction으로 나눴다(위 참조,
`tests/test_default_swap_locks.py`가 commit 분할과 lock 순서를 고정한다).
가장 오래된 날짜 파티션이 보존 기간+2일(운영 7일 기준 9일)보다 오래되면 `KorTravelWeatherRetentionStale`이
울린다(`ktw_oldest_partition_age_days`, API scrape 때 같은 카탈로그에서 읽는다). 스케줄은
KST 01:45다(2026-10-04~07 공용 Dagster run 기록상 동시 weather run이 가장 적은 시간; 옛
03:20은 03:15 외부 provider sweep과 겹쳤다).

`DETACH ... CONCURRENTLY`는 쓰지 않는다. PostgreSQL 16은 DEFAULT 파티션이 있으면
"cannot detach partitions concurrently when a default partition exists"로 거부하고, 이 테이블의
DEFAULT는 바닥 증명과 replay skip에 쓰여서 없앨 수 없다(없애려면 ingest 쪽 skip 창도 바꿔야
한다 — 소유자 결정 사항). lock 순서는 측정으로 정했다: `CREATE TABLE ... PARTITION OF`와
`DETACH`는 `weather_source_records`·`weather_locations`에 SHARE ROW EXCLUSIVE를, detach된
파티션의 `DROP`은 그 둘에 ACCESS EXCLUSIVE를 문장 중간에 잡는다. 그래서 정리 job은 그 둘을
먼저(수집과 같은 순서로) 잡고, detach와 drop을 따로 commit한다. 예전 순서는 수집 transaction과
교착해 수집 쪽을 죽였다(`tests/test_retention_under_ingest.py`).

**규칙 파일 반영.** 운영 weather Prometheus(`kor-travel-weather-prometheus`, host network
`:14104`)는 Manager #452(2026-10-03)부터 이 체크아웃의 `deploy/prometheus` **디렉터리**를
`/etc/prometheus/weather-rules`로 bind하고 `weather-rules/alerts.yml`을 읽는다. 그 전의
파일 하나 bind는 git이 바꾼 inode를 따라가지 못해 2026-09-04 이후 규칙 변경이 반영되지
않았다. 지금은 체크아웃을 갱신한 뒤 Prometheus에 SIGHUP을 보내면 된다(컨테이너 재생성 불필요).
Manager의 weather `ensure`는 init step `weather-prometheus-rules-reload`로 이것을 자동으로
한다. 규칙만 바꾼 배포의 절차는 `docs/observability.md` "규칙 변경 배포"에 있다.

만든 뒤에는 유효성을 확인한다.

이름 패턴이 아니라 만든 이름을 그대로 적는다. `IF NOT EXISTS`는 이름만 같으면
넘어가므로, 정의가 다른 인덱스가 남았는지 `indexdef`로 직접 확인한다.

```sql
SELECT c.relname, i.indisvalid, pg_get_indexdef(c.oid)
FROM pg_class c JOIN pg_index i ON i.indexrelid = c.oid
WHERE c.relname = ANY (ARRAY[
  'ix_weather_values_marker_observed',
  'ix_weather_values_alert_lookup',
  'ix_weather_current_values_alert_lookup',
  'ix_weather_current_values_location_current'
])
ORDER BY c.relname;
```

### 0016 배포 시점: Dagster storage를 PostgreSQL로 옮긴다

`deploy/dagster.yaml`이 `run_storage`/`event_log_storage`/`schedule_storage`를
`DAGSTER_POSTGRES_URL`로 지정하는 시점부터, 그 변수를 가리키는 데이터베이스가
먼저 존재해야 `dagster` 컨테이너가 기동한다. 이유는 `deploy/dagster.yaml`의
주석에 있다 — 지정하지 않으면 `DAGSTER_HOME`의 SQLite 파일로 떨어지는데, SQLite는
writer가 하나뿐이라 동시 실행 10개(+daemon)가 `sqlite3.OperationalError:
database is locked`로 서로 부딪힌다. STEP_SUCCESS/RUN_SUCCESS 이벤트가 그 경합에서
지면 run이 영원히 STARTED로 남는데, 프로세스는 실제로 살아 있어서
`run_monitoring`이 건드릴 이유가 없다 — 실행 이력이 SQLite에 남아 있던 동안 매번
발생한 정지의 실제 원인이었다.

DB는 앱 자신의 `weather`와 **분리한다**: `dagster-postgres`는 자기 스키마를
자기 Alembic으로 관리하고, 그 이력 테이블 이름도 `alembic_version`이라서 같은
DB에 두면 이 프로젝트의 `alembic_version`과 충돌한다.

```bash
ssh digitie@192.168.1.14 'cd ~/kor-travel-weather &&   docker compose --env-file .env -f compose.yaml -f deploy/compose.n150.yaml     exec -T db psql -U "$POSTGRES_USER" -d postgres -c     "SELECT 1 FROM pg_database WHERE datname = '"'"'weather_dagster'"'"'"'
# 위가 빈 결과면(존재하지 않으면) 만든다. dagster 컨테이너가 처음 시작할 때 여기에
# 테이블 22개를 스스로 만든다 -- 앱 쪽처럼 미리 만들어 둘 필요는 없다.
ssh digitie@192.168.1.14 'cd ~/kor-travel-weather &&   docker compose --env-file .env -f compose.yaml -f deploy/compose.n150.yaml     exec -T db psql -U "$POSTGRES_USER" -d postgres -c     "CREATE DATABASE weather_dagster OWNER \"$POSTGRES_USER\""'
```

이 전환은 기존 SQLite에 있던 실행 이력을 옮기지 않는다 -- 새 저장소는 빈 채로
시작하고, 예전 실행 목록은 Dagster UI에서 더 이상 보이지 않는다(도커 볼륨의
SQLite 파일 자체는 지워지지 않지만, 이후로는 아무도 읽지 않는다). 실행 이력은
운영 가시성 용도일 뿐 감사 기록이 아니므로, 이 배포 한 번은 그 손실을 감수한다.

Compose는 `migrate` one-shot을 먼저 성공시킨 뒤 API/Dagster를 기동한다. 실패한
migration을 복구할 때는 원격 프로젝트에서 다음을 실행한다.

```bash
docker compose --env-file .env \
  -f compose.yaml -f deploy/compose.n150.yaml run --rm migrate
docker compose --env-file .env \
  -f compose.yaml -f deploy/compose.n150.yaml ps
docker compose --env-file .env \
  -f compose.yaml -f deploy/compose.n150.yaml exec -T db \
  sh -lc 'PGPASSWORD="$POSTGRES_PASSWORD" psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" \
  -Atc "select version_num from alembic_version"'
```

기본 Compose는 loopback에 바인딩한다. n150 override는 API/Dagster/web만
`192.168.1.14`에 바인딩해 외부 HAProxy가 접근할 수 있게 하며, DB는 loopback-only로
유지한다. n150 방화벽에서는 HAProxy source만 애플리케이션 포트에 허용하고, 이 포트를
인터넷에 직접 공개하지 않는다. override를 사용하지 않는 임시 확인에는 인증된 SSH
tunnel을 사용한다.

n150 override는 web 로그인 rate-limit을 위해 `WEATHER_UI_TRUST_PROXY=true`를 사용한다.
HAProxy는 요청자가 보낸 `X-Forwarded-For`를 먼저 제거하고 연결된 client IP를 마지막
hop으로 append해야 한다. 이 헤더 경계를 지키지 못하는 경우에는 override의 해당 값을
`false`로 유지하고 gateway/WAF에서 로그인 rate-limit을 제공한다.

```bash
ssh -N \
  -L 14101:127.0.0.1:14101 \
  -L 14102:127.0.0.1:14102 \
  -L 14104:127.0.0.1:14104 \
  -L 14105:127.0.0.1:14105 \
  digitie@192.168.1.14
```

HAProxy upstream은 다음 주소를 사용한다.

```text
weather-api.digitie.mywire.org     -> 192.168.1.14:14101
weather-dagster.digitie.mywire.org -> 192.168.1.14:14102
weather.digitie.mywire.org         -> 192.168.1.14:14105
```

`GIT_COMMIT`은 build arg로 이미지에 구워진다. `git describe --dirty`를 쓰므로
커밋되지 않은 수정이 남은 채로 배포하면 `abc1234-dirty`로 드러난다 — sha만
구우면 그 수정을 포함하지 않는 커밋을 답해 원래 사고가 재현된다.
**`.env`에 `GIT_COMMIT`을 적지 마라.** `--env-file`로 넘긴 값도 compose 보간에
쓰이므로(셸 값이 있으면 셸이 이긴다) 셸에서 계산하지 않은 배포가 그 고정 값을
이미지에 구워 넣는다 — 손으로 채운 값이 낡는 이 사고의 원래 형태다.
저장소의 계약 테스트는 `.env.example`만 볼 수 있고 배포 `.env`는 볼 수 없다. 런타임 env가 아니므로 컨테이너를
재시작해도 이미지 안의 코드와 어긋나지 않는다. 빼먹으면 `/version`이 `unknown`을
답하므로 어떤 리비전인지 모른다는 사실이 즉시 드러난다 — 예전처럼 낡은 값을
그럴듯하게 보고하지 않는다. `/version`의 `git_commit`이 방금 배포한 리비전과
일치하는지 배포 후 반드시 확인한다.

배포 후 `/health`, `/version`, admin token을 사용한 위치 조회, Dagster GraphQL
repository/schedule 상태를 확인한다. 외부 reverse proxy 도메인도 다음처럼 확인한다.

```bash
curl -fsS https://weather-api.digitie.mywire.org/health
# git_commit이 방금 배포한 리비전과 같아야 한다. unknown이면 GIT_COMMIT 없이 빌드된 것이다.
curl -fsS https://weather-api.digitie.mywire.org/version
curl -u admin:'<WEATHER_UI_PASSWORD>' -fsS https://weather-dagster.digitie.mywire.org/server_info
# Web UI는 브라우저에서 /login으로 signed session을 발급한다.
curl -fsS -o /dev/null -w '%{http_code}\n' https://weather.digitie.mywire.org/login
# Use a protected SSH tunnel for local Prometheus checks; do not publish 14104.
curl -fsS -H "Authorization: Bearer $KOR_TRAVEL_WEATHER_METRICS_TOKEN" \
  http://127.0.0.1:14101/metrics | head
curl -fsS http://127.0.0.1:14104/-/ready
curl -fsS http://127.0.0.1:14104/api/v1/targets \
  | jq '[.data.activeTargets[] | {job,health,lastError}]'
```

target과 KMA key가 비어 있는 기본 설정은
서비스 기동 smoke만 제공하며, 실제 날씨 수집은 운영 설정을 채운 뒤에 검증한다.

### dagster 컨테이너 하나를 세 개로 분리한다

`dagster dev` 하나가 webserver+daemon+code-server를 한 프로세스로 묶어서
돌리고 있었다. 이 프로세스 안에서 실제로 코드를 import해서 실행하는 내부
worker(`dagster api grpc`)가 30초 heartbeat를 못 받으면 (호스트가 n150의
다른 프로젝트들과 CPU/메모리를 다투는 동안 부모 프로세스 자신의 heartbeat
송신 스레드가 지연되면서) 스스로 종료했는데, `dagster dev`의 자체 감시는
바깥쪽 프록시 프로세스가 살아 있는지만 확인하고 그 프록시가 내부적으로
관리하는 worker가 죽었는지는 전혀 보지 않아서, 죽은 뒤로는 아무것도 그걸
재시작하지 않았다. 컨테이너 자체는 "Up"으로 남아 있어서 `restart:
unless-stopped`도 발동하지 않았고, 8시간 동안 모든 job이 실패로 보이다가
수동 재시작으로 발견됐다.

`dagster-code-server`(`dagster api grpc`, `--heartbeat` 없이)가
`dagster-webserver`/`dagster-daemon`으로부터 완전히 분리된 컨테이너가 되면서
이 heartbeat 자체가 없어졌다 -- 이제 code-server는 진짜 크래시/OOM
때만 죽고, 그건 이미 다른 모든 서비스와 똑같이 `restart: unless-stopped`가
처리한다. `deploy/workspace.yaml`이 webserver/daemon을
`grpc_server: {host: dagster-code-server, port: 14106}`로 가리키고,
`deploy/prometheus/prometheus.yml`의 스크레이프 타겟과
`deploy/nginx/dagster-gateway.conf`의 업스트림도 각각
`dagster-code-server:14103`/`dagster-webserver:14102`로 옮겨졌다.
`deploy/dagster.yaml`(Postgres storage/run_monitoring/run_coordinator
설정)은 프로세스 토폴로지와 무관해서 변경 없음.

이 분리 전에 임시로 붙였던 `deploy/dagster-entrypoint.sh` watchdog(코드
위치가 막히면 GraphQL `reloadRepositoryLocation`으로 먼저 재시도하고, 그래도
안 되면 프로세스를 강제 종료하던 스크립트)는 이제 필요 없어져서 삭제했다 --
이 실패 유형 자체가 이 토폴로지에서는 발생할 수 없기 때문이다.

`dagster-code-server`는 실제 job 코드가 도는 컨테이너라 리소스 튜닝도
여기에 붙였다: `cpu_shares: 4096`(경합 시에만 우선권, 유휴 시 비용 0),
`mem_reservation: 2g`/`mem_limit: 4g`, `mem_swappiness: 10`,
`oom_score_adj: -500`. `cpus:`(하드 CFS quota)는 일부러 안 걸었다 -- 이
컨테이너를 지키려는 목적에 오히려 역효과(스로틀이 새 지연을 자체 생산)이기
때문이다.

### `kor-travel-docker-manager` 공유 제어 평면 대비: code-server를 loopback에 publish

`kor-travel-docker-manager`의 `docs/platform-topology.md` §7(2026-09-19
결정, 아직 미구현)은 여러 프로젝트(map/geo/conc/pinvi/weather)가 공유
`dagster-webserver`/`dagster-daemon` 하나를 같이 쓰고, code-server만
프로젝트별로 분리 유지하는 걸 목표로 한다. weather의 code-server 분리(바로
위 항목)가 그 §7 1단계의 참조 구현으로 인용됐다.

공유 webserver/daemon이 weather의 code-server를 `workspace.yaml`의
`grpc_server`로 등록하려면 weather의 compose 네트워크 밖에서 접근할 수
있어야 한다. `dagster-code-server`에 `ports: ["127.0.0.1:14106:14106"]`를
추가해 뒀다 -- LAN(`192.168.1.14`)이 아니라 **loopback만**이다. 이 gRPC
포트엔 `dagster-gateway`의 Basic Auth 같은 보호가 전혀 없어서(코드 실행·run
launch까지 가능한 bare code-server), 호스트 자신만 접근 가능해야 한다.
pinvi/geo가 이미 채택한 `network_mode: host` + loopback 패턴과 같은 이유로,
공유 webserver/daemon이 host network로 뜨면 이 loopback 바인딩으로 바로
닿는다.

**아직 안 한 것** (§7 2~4단계, Manager 쪽 작업 완료 후에나 가능):
공유 Postgres(`dagster_shared`)로 weather의 Dagster 메타데이터를 옮기는 것,
weather 자신의 `dagster-webserver`/`dagster-daemon`을 내리는 것. 옛
`weather_dagster` DB의 run 이력은 옮기지 않기로 했다 -- 공유 인스턴스는
그 시점부터 새로 쌓인다.

  rate-limit" 단락)는 **불변**이지만 **값의 자리는 Manager root `.env`**다 — Manager compose는
  `WEATHER_UI_TRUST_PROXY: ${WEATHER_UI_TRUST_PROXY:-}`·`WEATHER_UI_PUBLIC_ORIGIN:
  ${WEATHER_UI_PUBLIC_ORIGIN:-}`(`docker-compose.yml:3160-3161`)로 root `.env`를 통과시킬 뿐이고

  저장소 `compose.yaml:117`의 기본값(`http://127.0.0.1:14105`)은 standalone용이며 손대지 않는다.

  comprehension으로 생성, `:1272-1281`), 일 2회 2개(`30 6,18`·`30 5,17`), 일 1회 1개(`45 1`, 야간 정리).

### 메모리·swap — 두 층

- **규칙(리터럴, 두 호스트 동일 — T-MGR-03, ADR-58 결정 8(ⅳ))**: "`mem_limit`가 있는 서비스마다
  `memswap_limit == mem_limit`(**같은 변수**)". weather code-server의 다른 설정 `cpu_shares 4096`·
  `mem_reservation 2g`·`mem_swappiness 10`·`oom_score_adj -500`·`pids_limit 2048`(Manager
  `docker-compose.yml:2872-2877`; 이 저장소 `compose.yaml:265-270`과 같다)은 **유지**한다. odroid는
  cgroup v1에 swap accounting이 켜져 있어(실측) `memswap_limit`가 없으면 Docker 기본값 2×로 swap까지
  천장이 되고 "limit 도달 = OOM = run FAILURE"가 성립하지 않는다. n150(cgroup v2)에서는
  `memory.swap.max=0`과 같은 뜻이다.
- **값(호스트별, env 파생 — ADR-58 결정 8(ⅱ))**: `mem_limit`는 리터럴이 아니라 T-MGR-03이 Manager
  compose를 `${KTDM_…_MEM_LIMIT:-4g}` 꼴로 바꾼 **env 파생**이다(변수 이름은 T-MGR-03이 정한다;
  `docs/tasks.md` T-MGR-03 "weather cs는 `${…:-4g}`(odroid `.env` 1.5g)"). compose 기본값 **4g = n150
  현재 상태**(n150 root `.env`는 아무것도 적지 않는다), **odroid root `.env`가 1.5g**를 준다 — ADR-58
  결정 8(ⅱ) "weather cs 1.5g(초과 시 배치 축소)"·(ⅳ) "weather cs는 n150 4g/odroid 1.5g 각각".
  `memswap_limit`는 같은 변수를 쓰므로 odroid에서 1.5g로 **자동으로 같이** 내려간다(별도 조치 없음).
  Manager compose 블록에 1.5g를 직접 쓰면 n150도 1.5g가 되고 T-MGR-03의 "리터럴 ≠ env" 테스트와
  충돌하므로 하지 않는다. 설계 실측 반영 기록 #20의 "weather 4g; 리터럴 두 호스트 동일"은 **규칙**
  (memswap == mem_limit)에 대한 말이고 값은 ADR-58이 갱신했다 — ADR을 따른다.
- **T-WEA-02, odroid 한도 운영 기록**: odroid RAM은 7,676 MiB(실측)이고 Plex·Samba 등 보존 서비스가
  공존하므로 1.5g다. 적용 시점은 §14-1 n150 선행 실측(매시 run p95·hot set) 뒤이고, 수용 기준은
  weather 3h/12h run이 포함된 24 h 창에서 OOM-kill 0. 초과 시 조정 손잡이는
  `KOR_TRAVEL_WEATHER_MAX_PAYLOAD_BYTES_PER_RUN`(`compose.yaml:60`, 기본 16 MiB) 배치 축소다(값의
  자리는 역시 odroid root `.env`). 과제 정의는 아래 "후속 작업".

### 시계 — 파티션 바닥·forward window가 호스트 시계에 묶여 있다

odroid는 RTC가 2017, 시스템 시계가 2023이던 호스트다(2026-10-13 03:38Z에 수동 NTP 동기로 2026에
맞췄고 RTC도 갱신됐다 — 단 아래 "odroid 상태" 참조). 시계가 틀린 채 weather가 돌면:

- `known_at`이 과거(2023)인 fact는 DEFAULT 바닥 아래라 DEFAULT로 들어가고 **retention이 영원히
  닿지 않는다**; 반대로 시계가 앞서면 forward window 밖이라 **적재가 거부된다**
  (`src/kortravelweather/partitions.py:113-130`, `DEFAULT_FLOOR_CONSTRAINT` 주석). 야간 정리는
  2023 날짜 기준으로 forward 파티션을 만든다.
- odroid Prometheus의 `/federate` 샘플은 odroid 타임스탬프를 달고 가므로 n150이 out-of-bounds로
  **조용히 버린다**(`docs/observability.md`).
- data.go.kr·KMA TLS가 not-yet-valid로 실패해 run FAILURE가 provider 장애로 분류된다.

그래서 ADR-58은 NTP를 모든 설치 단계의 **전제**로 두고, `time-sync.target` 뒤에 Docker·Manager가
뜨도록 부팅 순서를 묶는다(절차는 Manager `docs/prod-deployment.md` §9.1 ⓪~④; 방식은 추천, §14-25:
timesyncd가 부팅마다 큐잉되지 않는 사이클이 있어 보존 unit drop-in으로 먼저 끊고 재부팅 2회 PASS
뒤에만 `After=time-sync.target`을 넣는다 — 그 전에 넣으면 Docker가 영구 미기동). 중단선(§14-16):
그 drop-in이 불가하거나 재부팅 2회 검증 실패.
