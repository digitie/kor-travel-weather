# n150 운영 기록

이 문서는 `n150`에 배포할 때 사용하는 비밀값이 없는 운영 기록이다.

| 항목 | 값 |
| --- | --- |
| 호스트 | `digitie@192.168.1.14` |
| 프로젝트 경로 | `~/kor-travel-weather` |
| 데이터베이스 | PostgreSQL, `127.0.0.1:14100` |
| API | `192.168.1.14:14101` (LAN override) |
| Dagster | `192.168.1.14:14102` (LAN override) |
| admin web | `192.168.1.14:14105` (LAN override) |

운영 HTTPS 도메인은 다음과 같다.

| 서비스 | 운영 URL |
| --- | --- |
| API | `https://weather-api.digitie.mywire.org` |
| Dagster | `https://weather-dagster.digitie.mywire.org` |
| admin web | `https://weather.digitie.mywire.org` |

Prometheus는 `14104` loopback에만 바인딩되며 public 도메인/HAProxy에 연결하지
않는다. API scrape에는 별도의 `KOR_TRAVEL_WEATHER_METRICS_TOKEN`(admin token과
다른 16자 이상 secret)이 필요하다. 이 secret은 API와 Prometheus에만 주입한다.

admin web 로그인 아이디는 `admin`으로 고정한다. 비밀번호는 배포 secret 파일에서
`WEATHER_UI_PASSWORD`로 주입하며 signed session 로그인 form에서만 사용한다.
Basic Auth는 Dagster gateway에만 적용하며 저장소에는 비밀번호를 기록하지 않는다.

## 배포

원격 `~/kor-travel-weather/.env`는 모드 `600`으로 유지하고 Git에 추가하지 않는다.
비밀값은 password manager/secret manager에서 일회성으로 주입하고, 저장소 작업
복사본에는 평문 secret 파일을 남기지 않는다. `KOR_TRAVEL_WEATHER_CREDENTIAL_ENCRYPTION_KEY`와
`KOR_TRAVEL_WEATHER_METRICS_TOKEN`도 API와 관련 서비스에 동일하게 주입해야
`/settings/providers`에서 암호화된 DB override를
저장할 수 있다. KMA service key와 수집 target은
운영자가 발급·검토한 뒤에만 원격 secret store에서 주입한다.

```bash
# 예: 보호된 로컬 secret 파일을 사용한다(저장소 안에 만들지 않는다).
scp /secure/path/kor-travel-weather-n150.env digitie@192.168.1.14:~/kor-travel-weather/.env
ssh digitie@192.168.1.14 \
  'chmod 600 ~/kor-travel-weather/.env && cd ~/kor-travel-weather && \
   git fetch origin && git checkout main && git pull --ff-only && \
   docker compose --env-file .env \
     -f compose.yaml -f deploy/compose.n150.yaml up -d --build'
```

### 인덱스 마이그레이션은 배포 창 밖에서 먼저 만든다

`0009`~`0011`과 `0013`은 `CREATE INDEX CONCURRENTLY`를 쓴다. CONCURRENTLY는 병렬 워커를
쓰지 않고 테이블을 두 번 훑으며, `weather_values`는 2천만 행/28GB 규모다.
API와 Dagster는 `migrate: service_completed_successfully`에 묶여 있으므로 그
빌드가 끝날 때까지 **공개 API가 내려가 있다**. 인덱스 4개를 배포 중에 만들면
그 창이 수십 분에 이를 수 있다.

배포 전에 psql로 먼저 만들어 두면 마이그레이션의 `IF NOT EXISTS`가 그대로
통과한다. 이름만 같으면 넘어가므로 **아래 문장을 그대로** 써야 한다 — 정의가
다르면 마이그레이션은 손대지 않고, 잘못된 인덱스가 그대로 남는다.

```bash
ssh digitie@192.168.1.14 'docker exec -i kor-travel-weather-db-1 \
  psql -v ON_ERROR_STOP=1 -U weather -d weather' <<'SQL'
CREATE INDEX CONCURRENTLY IF NOT EXISTS ix_weather_values_marker_observed
  ON weather_values (location_id, metric_key, known_at DESC NULLS LAST,
                     source_record_key DESC NULLS LAST, value_id DESC)
  WHERE metric_key IN ('TEMP', 'T1H', 'TMP', 'WEATHER_CODE', 'SKY', 'PTY')
    AND forecast_style IN ('observed', 'nowcast');
CREATE INDEX CONCURRENTLY IF NOT EXISTS ix_weather_values_alert_lookup
  ON weather_values (location_id, target_at DESC)
  WHERE weather_domain = 'weather_alert' OR metric_key = 'ALERT';
CREATE INDEX CONCURRENTLY IF NOT EXISTS ix_weather_current_values_alert_lookup
  ON weather_current_values (location_id, target_at DESC)
  WHERE metric_key = 'ALERT' OR weather_domain ILIKE '%alert%'
     OR weather_domain ILIKE '%warning%' OR dataset_key ILIKE '%alert%'
     OR dataset_key ILIKE '%warning%';
SQL
```

`0013`의 인덱스는 `0012`가 추가하는 컬럼 위에 만들어지므로 같은 블록에 넣을 수
없다. 위 블록에 섞어 두면 스키마가 아직 `0011`이라 `column "known_at" does not
exist`로 실패하는데, **psql은 그래도 exit 0을 반환**해 운영자는 네 개가 다
준비됐다고 믿게 된다. 그래서 `-v ON_ERROR_STOP=1`을 쓰고, 0012만 먼저 적용한 뒤
별도 블록으로 만든다. 0012는 아래 설명대로 API를 막지 않는다.

```bash
ssh digitie@192.168.1.14 'cd ~/kor-travel-weather && \
  docker compose --env-file .env \
    -f compose.yaml -f deploy/compose.n150.yaml \
    run --rm migrate alembic upgrade 0012_current_value_sort_keys'

ssh digitie@192.168.1.14 'docker exec -i kor-travel-weather-db-1 \
  psql -v ON_ERROR_STOP=1 -U weather -d weather' <<'SQL'
CREATE INDEX CONCURRENTLY IF NOT EXISTS ix_weather_current_values_location_current
  ON weather_current_values
  (location_id,
   (CASE WHEN forecast_style IN ('observed', 'nowcast') THEN 0 ELSE 1 END),
   target_at DESC, known_at DESC NULLS LAST,
   source_record_key DESC NULLS LAST, value_id DESC);
SQL
```

Dagster 수집이 도는 시각(매시 정각·10분)은 피한다. CONCURRENTLY는 동시
트랜잭션이 끝나기를 기다리므로, 대량 publish 트랜잭션 뒤에서 그만큼 지연된다.
인덱스 빌드가 실패해 INVALID 인덱스가 남아도 해당 마이그레이션이 회수하고 다시
만든다(`indisvalid`만 확인한다). 이는 인덱스 리비전(0009~0011, 0013)에 대한
이야기다 — 0012는 인덱스를 만들지 않고, 대신 위 설명대로 재실행 안전하다.
**migrate 컨테이너를 중간에 죽이지 말 것** — 다음 시도가 처음부터 다시 돈다.

### 0012는 사전 생성 대상이 아니다 (그럴 필요도 없다)

`0012`는 인덱스가 아니라 `weather_current_values`에 컬럼 두 개를 더하고 채운다.
nullable 컬럼 추가는 카탈로그만 바꾸므로 `ACCESS EXCLUSIVE`를 밀리초 단위로만
잡고 테이블 재작성이 없다. 이어지는 백필은 평범한 `UPDATE`를 배치로 돌아 행
잠금만 쓰므로 **읽기를 막지 않는다**. 둘을 한 문장으로 합치면 28GB 팩트 테이블
순차 스캔 내내 배타 잠금을 쥐게 되어 API 전체가 멈추는데, 그래서 나눠 놓았다.

백필은 이어서 돌릴 수 있다. 고르는 기준은 "키가 비어 있는 행"이 아니라 **"키가
가리키는 팩트와 어긋난 행"**이다. 이전 릴리스는 포인터를 옮길 때 `value_id`만
쓰므로(새 컬럼이 모델에 없다) 그 행은 새 팩트를 가리키면서 이전 팩트의 키를
그대로 들고 있게 된다 — 비어 있지 않고 틀린 상태다. 컬럼 추가도
`IF NOT EXISTS`다. alembic은 `upgrade()`가 끝난 뒤에야 버전을 기록하므로, 그
전에 커밋되는 것은 전부 다시 실행해도 안전해야 한다.

컬럼은 nullable로 둔다. compose는 이전 릴리스가 아직 수집·서빙하는 동안
migrate를 돌리고, 그 릴리스는 새 컬럼 없이 포인터 행을 쓴다. 여기서 `NOT NULL`을
걸면 배포 도중 수집이 깨진다. 그 창에서 쓰인 행은 정렬에서 뒤로 밀리고
(`nullslast`) 해당 논리 지점의 다음 리비전에서 키를 얻는다.

### 롤백 순서

`0012`를 되돌리면 컬럼이 사라진다. **먼저 이전 릴리스를 배포한 뒤** 되돌려라.
현재 코드가 도는 상태에서 컬럼을 지우면 번들 조회가 전부 `UndefinedColumn`으로
500을 내는데 `/health`는 200이라 알람이 울리지 않는다.

만든 뒤에는 유효성을 확인한다.

이름 패턴이 아니라 만든 이름을 그대로 적는다. `IF NOT EXISTS`는 이름만 같으면
넘어가므로, 정의가 다른 인덱스가 남았는지 `indexdef`로 직접 확인한다.

```sql
SELECT c.relname, i.indisvalid, pg_get_indexdef(c.oid)
FROM pg_class c JOIN pg_index i ON i.indexrelid = c.oid
WHERE c.relname = ANY (ARRAY[
  'ix_weather_values_marker_observed',
  'ix_weather_values_alert_lookup',
  'ix_weather_current_values_alert_lookup',
  'ix_weather_current_values_location_current'
])
ORDER BY c.relname;
```

Compose는 `migrate` one-shot을 먼저 성공시킨 뒤 API/Dagster를 기동한다. 실패한
migration을 복구할 때는 원격 프로젝트에서 다음을 실행한다.

```bash
docker compose --env-file .env \
  -f compose.yaml -f deploy/compose.n150.yaml run --rm migrate
docker compose --env-file .env \
  -f compose.yaml -f deploy/compose.n150.yaml ps
docker compose --env-file .env \
  -f compose.yaml -f deploy/compose.n150.yaml exec -T db \
  sh -lc 'PGPASSWORD="$POSTGRES_PASSWORD" psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" \
  -Atc "select version_num from alembic_version"'
```

기본 Compose는 loopback에 바인딩한다. n150 override는 API/Dagster/web만
`192.168.1.14`에 바인딩해 외부 HAProxy가 접근할 수 있게 하며, DB는 loopback-only로
유지한다. n150 방화벽에서는 HAProxy source만 애플리케이션 포트에 허용하고, 이 포트를
인터넷에 직접 공개하지 않는다. override를 사용하지 않는 임시 확인에는 인증된 SSH
tunnel을 사용한다.

n150 override는 web 로그인 rate-limit을 위해 `WEATHER_UI_TRUST_PROXY=true`를 사용한다.
HAProxy는 요청자가 보낸 `X-Forwarded-For`를 먼저 제거하고 연결된 client IP를 마지막
hop으로 append해야 한다. 이 헤더 경계를 지키지 못하는 경우에는 override의 해당 값을
`false`로 유지하고 gateway/WAF에서 로그인 rate-limit을 제공한다.

```bash
ssh -N \
  -L 14101:127.0.0.1:14101 \
  -L 14102:127.0.0.1:14102 \
  -L 14104:127.0.0.1:14104 \
  -L 14105:127.0.0.1:14105 \
  digitie@192.168.1.14
```

HAProxy upstream은 다음 주소를 사용한다.

```text
weather-api.digitie.mywire.org     -> 192.168.1.14:14101
weather-dagster.digitie.mywire.org -> 192.168.1.14:14102
weather.digitie.mywire.org         -> 192.168.1.14:14105
```

배포 후 `/health`, `/version`, admin token을 사용한 위치 조회, Dagster GraphQL
repository/schedule 상태를 확인한다. 외부 reverse proxy 도메인도 다음처럼 확인한다.

```bash
curl -fsS https://weather-api.digitie.mywire.org/health
curl -u admin:'<WEATHER_UI_PASSWORD>' -fsS https://weather-dagster.digitie.mywire.org/server_info
# Web UI는 브라우저에서 /login으로 signed session을 발급한다.
curl -fsS -o /dev/null -w '%{http_code}\n' https://weather.digitie.mywire.org/login
# Use a protected SSH tunnel for local Prometheus checks; do not publish 14104.
curl -fsS -H "Authorization: Bearer $KOR_TRAVEL_WEATHER_METRICS_TOKEN" \
  http://127.0.0.1:14101/metrics | head
curl -fsS http://127.0.0.1:14104/-/ready
curl -fsS http://127.0.0.1:14104/api/v1/targets \
  | jq '[.data.activeTargets[] | {job,health,lastError}]'
```

target과 KMA key가 비어 있는 기본 설정은
서비스 기동 smoke만 제공하며, 실제 날씨 수집은 운영 설정을 채운 뒤에 검증한다.
